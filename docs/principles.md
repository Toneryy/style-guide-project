# Общие принципы

## Зачем нужно руководство

Документацию Itmotify пишут разные люди: аналитик, разработчики, тестировщик, музыкальный редактор. Без общих правил каждый пишет по-своему, и читатель тратит силы на то, чтобы привыкнуть к новому автору. Руководство решает пять задач:

- документы выглядят и читаются одинаково, кто бы их ни написал;
- автор не тратит время на вопросы «как здесь принято» ;
- новый участник команды за один вечер узнаёт, как устроена документация;
- рецензент проверяет документ по правилам, а не по вкусу;
- читатель знает, где искать нужное, потому что структура и термины везде одинаковые.

Все документы, кроме ТЗ, хранятся в Markdown в репозиториях проекта. ТЗ оформляется в формате DOCX по стандарту, но формулировки требований подчиняются этому руководству.

## Пять принципов

### Читатель и задача

Перед тем как писать, ответьте на два вопроса: кто будет читать и что он хочет сделать после прочтения. Одна справочная статья решает одну задачу. Если задач две, напишите две статьи и свяжите их ссылками.

### Ясность

Пишите короткими предложениями и общеупотребительными словами. Убирайте всё, что не помогает читателю: вводные слова, канцелярит, повторы. Подробнее — в разделе [Стиль изложения](style.md).

### Единообразие

Одно понятие — один термин во всех документах. Термины берите из [глоссария](glossary.md). Похожие документы стройте по одному шаблону.

### Проверяемость

Каждое утверждение можно проверить. В справке это означает точные названия кнопок и разделов, в требованиях — числа и условия вместо оценок. Подробнее — в разделе [Требования и ТЗ](requirements.md).

### Ревью

Ни один документ не публикуется без проверки вторым человеком. Ревью проходит через Pull Request, автоматические проверки запускаются до ревью.

## Чек-лист автора

Перед тем как отправить документ на ревью, проверьте:

- [ ] определено, кто читатель и какую задачу он решает;
- [ ] документ построен по шаблону;
- [ ] термины совпадают с глоссарием;
- [ ] названия элементов интерфейса совпадают с тем, что видно на экране;
- [ ] в требованиях нет оценочных слов, у каждого требования есть критерий проверки;
- [ ] линтеры markdownlint и Vale не выдают ошибок;
- [ ] сайт собирается командой `mkdocs build --strict`.
