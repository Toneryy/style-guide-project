# Требования и ТЗ

Раздел для аналитиков и всех, кто пишет требования к Itmotify. Структуру ТЗ задает стандарт, по которому оно оформляется. Этот раздел описывает, как формулировать сами требования.

## Одно требование – один пункт

- В пункте одно требование, которое можно реализовать и проверить отдельно от других.
- Если в пункте есть «и», «а также», «или», проверьте, не два ли это требования.
- У каждого требования есть идентификатор: `ФТ-01` для функциональных, `НФТ-01` для нефункциональных. Номер не меняется, даже если требование удалили: удаленное помечается как «Исключено».

## Формула требования

Пишите по шаблону:

> **Субъект** + **должен** + **действие** + **объект** + **условие** + **критерий проверки**

Пример: «Система должна возвращать результаты поиска по названию трека не более чем за 2 с для 95 % запросов при нагрузке 1000 запросов в секунду».

| Часть | Что пишем | Пример |
| --- | --- | --- |
| Субъект | Кто выполняет: «Система», «Пользователь», «Музыкальный редактор» | Система |
| Модальность | Насколько требование обязательно, см. ниже | должна |
| Действие | Глагол в инфинитиве | возвращать |
| Объект | С чем выполняется действие | результаты поиска по названию трека |
| Условие | При каких условиях | при нагрузке 1000 запросов в секунду |
| Критерий | Число, по которому тестировщик проверит требование | не более чем за 2 с для 95 % запросов |

## Модальность

| Слово | Значение |
| --- | --- |
| должна, должен | Обязательное требование. Без него выпуск не принимается |
| следует | Желательное требование. Если его не выполнить, нужно объяснить причину |
| может | Допустимая возможность. Реализуется, если хватит ресурсов |

<!-- vale Itmotify.Vague = NO -->
Не используйте «желательно», «по возможности», «при необходимости» – из них непонятно, обязательно ли требование и кто решает, что «необходимость» наступила.
<!-- vale Itmotify.Vague = YES -->

## Проверяемость

Требование проверяемо, если тестировщик может написать тест, который однозначно покажет: выполнено или нет. Оценочные слова заменяйте измеримыми критериями.

<!-- vale Itmotify.Vague = NO -->
| Неправильно | Правильно |
| --- | --- |
| ~~Интерфейс должен быть понятным и удобным.~~ | 9 из 10 участников юзабилити-теста должны создать плейлист без подсказок не более чем за 60 с. |
| ~~Поиск должен работать быстро.~~ | Система должна возвращать результаты поиска не более чем за 2 с для 95 % запросов. |
| ~~Система должна выдерживать большое количество пользователей.~~ | Система должна обслуживать 10 000 одновременных сессий воспроизведения без роста времени отклика выше 2 с. |
| ~~Основные действия должны выполняться за минимальное количество кликов.~~ | Воспроизведение трека из результатов поиска должно запускаться не более чем за 2 нажатия. |
<!-- vale Itmotify.Vague = YES -->

## Приоритет и источник

У каждого требования укажите:

- **приоритет** по методу MoSCoW: «Должно» (Must), «Следует» (Should), «Может» (Could), «Не в этом выпуске» (Won't);
- **источник**: заказчик, интервью с пользователями, анализ аналогов, требование закона;
- **критерий приемки**: как проверить на приемке.

## Термины в требованиях

- Используйте только термины из [глоссария](glossary.md). Если нужного термина нет, добавьте его в глоссарий в том же Pull Request.
- Не заменяйте термин синонимом ради разнообразия. «Пользователь» в одном пункте и «клиент» в другом читатель поймет как двух разных людей.
- В ТЗ допустимы технические термины, которых нет в справке: «авторизация», «сессия», «лайк». В справке используйте пользовательские названия: «вход», «отметка **Нравится**».
