# Оформление текста

## Заголовки

- На странице один заголовок первого уровня — название документа. Он стоит в первой строке файла.
- Уровни идут по порядку: после второго уровня — третий, а не четвёртый.
- Глубже третьего уровня не опускайтесь. Если не хватает уровней, разделите документ на отдельные страницы.
- Заголовок статьи-инструкции — глагол в инфинитиве без «Как»: «Создать плейлист», «Оформить подписку Premium».
- Заголовок справочного раздела — существительное: «Рекомендации», «Подписка Premium».
- Заголовок не длиннее 60 знаков. Точку в конце не ставьте, номер в Markdown не пишите: MkDocs сам строит оглавление.

| Неправильно | Правильно |
| --- | --- |
| ~~Как можно создать свой плейлист?~~ | Создать плейлист |
| ~~3.2. Информация о подписке.~~ | Подписка Premium |

## Абзацы

- В абзаце одна мысль, обычно 2–4 предложения.
- Самое важное — в первом предложении абзаца. Читатель часто читает только начало.
- Не разрывайте абзац переносами строк внутри: в Markdown один абзац — одна строка.

## Списки

Используйте список, если перечисляете три и больше однородных элемента.

- **Нумерованный список** — для шагов, которые выполняются по порядку, и для элементов, на которые ссылаются по номеру.
- **Маркированный список** — когда порядок не важен.

Правила для пунктов:

- перед списком стоит вводное предложение с двоеточием;
- все пункты построены одинаково: все начинаются с глагола или все с существительного;
- если пункт — часть предложения, начинайте его со строчной буквы и заканчивайте точкой с запятой, а последний пункт — точкой;
- если пункт состоит из одного или нескольких законченных предложений, начинайте с прописной буквы и заканчивайте точкой;
- в списке не больше 9 пунктов, иначе разбейте его на группы с подзаголовками;
- вложенность — не больше двух уровней.

## Таблицы

- Используйте таблицу, если сравниваете объекты по двум и больше параметрам. Если параметр один, хватит списка.
- Перед таблицей пишите предложение, которое объясняет, что в ней.
- Заголовки столбцов — существительные с прописной буквы, без точки.
- В пустой ячейке ставьте тире «—», чтобы было видно, что значение не забыли.
- Не вкладывайте в ячейку списки и абзацы. Если содержимое не помещается, таблица не подходит.

## Выделение

| Приём | Когда используем |
| --- | --- |
| **Жирный** | Названия элементов интерфейса и важное предупреждение, не больше одного на абзац |
| `Моноширинный` | Код, команды, имена файлов, параметры и значения полей |
| Курсив | Не используем: на экране курсив читается хуже |
| ПРОПИСНЫЕ БУКВЫ | Не используем |
| Подчёркивание | Только для ссылок, это делает тема сайта |
| ~~Зачёркивание~~ | Только для примеров «как неправильно» в этом руководстве |

## Ссылки

- Текст ссылки описывает, куда она ведёт: «Подробнее — в разделе [Подписка Premium](glossary.md)».
- Ссылки на другие страницы руководства и документации — относительные, на файл `.md`: `[Глоссарий](glossary.md)`.
- Внешние ссылки — полные, с `https://`.
- Не вставляйте голый адрес в текст. Если адрес нужно показать, возьмите его в угловые скобки: `<https://itmotify.example>`.

## Иллюстрации

- Добавляйте скриншот, только если без него действие трудно понять. Каждый шаг всё равно описывайте текстом.
- У каждого изображения есть альтернативный текст, который передаёт смысл картинки.
- Перед публикацией закрасьте на скриншоте персональные данные: имя, почту, номер карты.
- Храните изображения рядом с разделом в папке `docs/assets/images/<раздел>/`. Имя файла — латиницей, строчными буквами, через дефис: `playlist-create-button.png`.
- Ширина скриншота — от 800 до 1200 пикселей. Обрезайте лишнее, оставляйте только нужную часть экрана.

## Код и команды

- Команды, имена файлов, параметры и значения полей оформляйте как код: `mkdocs serve`, `mkdocs.yml`, `site_name`.
- Многострочный код — в блоке с указанием языка: `bash`, `yaml`, `json`, `python`.
- Перед блоком кода пишите, что он делает. После — что должно получиться.
- В командах не ставьте приглашение `$` перед командой: читатель скопирует его вместе с командой.
