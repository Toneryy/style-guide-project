# Проверка руководства

Чтобы проверить руководство, мы применили его к двум документам Itmotify:

1. **Существующий документ** — подразделы 5.1.5 и 5.1.6 из ТЗ на разработку Itmotify. Команда писала это ТЗ в прошлом семестре без стайлгайда. Результат — [Требования ТЗ: до и после](nfr-rewrite.md).
2. **Новый документ** — справочная статья, написанная с нуля по шаблону. Результат — [Создать плейлист](create-playlist.md).

## Что проверяли

| Критерий | Вопрос |
| --- | --- |
| Применимость | Помогает ли руководство найти ошибки и исправить их? |
| Полнота | Хватило ли правил, или автору пришлось решать сам? |
| Однозначность | Дают ли правила один ответ, нет ли противоречий? |
| Автоматизация | Какую часть нарушений находят линтеры? |

## Результаты

### Требования ТЗ

- Нарушения нашлись во всех 10 исходных требованиях. Для каждого нарушения в руководстве есть правило, которое объясняет, как его исправить.
- После правки получилось 11 требований: пункт про персональные данные содержал два требования, и его пришлось разделить.
- Пункт 5.1.6.5 оказался целью, а не требованием. Правило «одно требование — один пункт» помогло разложить его на конкретные требования.
- Vale в первой версии правил нашёл замечания только в 3 пунктах из 10. После доработки словаря — в 5 пунктах из 10, всего 7 замечаний. Переписанный текст проходит проверку без замечаний.
- Отсутствие субъекта, условий и критерия приёмки линтер не находит. Эти нарушения находит только автор или рецензент по чек-листу.

### Справочная статья

- Шаблон задал структуру, и статья заняла три коротких раздела. Названия элементов, глаголы действий и путь через стрелку взяты из раздела [Интерфейс и действия](../ui.md) без доработки.
- Правило о кнопках со значком помогло назвать кнопку с тремя точками. При этом выяснилось, что в двух разделах руководства эта кнопка называлась по-разному.
- В шаблоне не было места для типичных проблем пользователя, а без него статья не отвечала на вопрос «что делать, если кнопки нет».
- Статья проходит markdownlint и Vale без замечаний.

## Что исправили в руководстве

<!-- vale Itmotify.Vague = NO -->
| Проблема | Изменение |
| --- | --- |
| Vale не находил оценочные выражения из требований к безопасности | В правило `Itmotify.Vague` добавлены «отзывчивый», «безопасным способом», «должен быть защищён» и «должен быть ограничен» |
| Отдельная таблица атрибутов для каждого из 11 требований делает текст громоздким | В шаблон [Требование](../templates/requirement.md) добавлен формат реестра требований |
| В шаблоне справочной статьи нет раздела о проблемах | В шаблон [Справочная статья](../templates/help-article.md) добавлен раздел «Если что-то не получилось» |
| Кнопка с тремя точками называлась **…** в одном разделе и **Ещё** в другом | Во всех разделах кнопка называется **Ещё** — по всплывающей подсказке |
| Не было правила для текста, который вводит пользователь | В раздел [Орфография и пунктуация](../spelling.md#кавычки) добавлено правило о ёлочках |

## Оценка

| Критерий | Оценка | Комментарий |
| --- | --- | --- |
| Применимость | Высокая | Каждое найденное нарушение исправлено по конкретному правилу |
| Полнота | Средняя, после доработки — высокая | Нашлись 3 пробела в правилах и шаблонах, все закрыты |
| Однозначность | Высокая | Нашлось 1 противоречие в названии кнопки, исправлено |
| Автоматизация | Средняя | Линтеры находят оформление и оценочные слова, но не смысловые ошибки требований |

Вывод: руководство подходит для работы. Правила о требованиях дают наибольший эффект — они превращают непроверяемые пожелания в требования, по которым можно написать тест. Линтеры не заменяют ревью, поэтому чек-лист автора и ревью в Pull Request остаются обязательными.
