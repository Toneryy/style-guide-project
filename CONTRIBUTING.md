# Как вносить изменения в руководство

Руководство живёт по правилам Docs as Code: каждое изменение проходит через ветку, Pull Request, автоматические проверки и ревью. Прямые коммиты в `main` не делаем — исключение составила только первоначальная настройка репозитория.

## Как предложить изменение

1. Если хотите обсудить идею до правки, создайте Issue. Опишите, какое правило мешает или чего не хватает, и приведите пример из реального документа.
2. Создайте ветку от свежего `main`. Название ветки — тип изменения и пара слов латиницей через дефис:

    ```bash
    git switch main
    git pull
    git switch -c docs/accessibility
    ```

3. Внесите изменения и проверьте их локально — см. [Локальная сборка](#локальная-сборка).
4. Сделайте коммит по правилам из раздела [Оформление коммитов](#оформление-коммитов) и отправьте ветку на GitHub: `git push -u origin docs/accessibility`.
5. Откройте Pull Request в `main`. Заголовок PR оформите так же, как коммит. Заполните шаблон описания.
6. Дождитесь, пока пройдут проверки, и попросите ревью.

## Оформление коммитов

Сообщения коммитов пишем по спецификации [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание>

<тело — по желанию: что и зачем изменено>
```

- **Тип** и **область** — латиницей, строчными буквами. Область — имя раздела или файла без расширения, её можно не указывать.
- **Описание** — на русском, со строчной буквы, глагол в инфинитиве, без точки в конце, до 72 знаков.
- Если изменение отменяет или противоречит прежнему правилу, поставьте `!` после типа и объясните в теле, что изменилось для авторов.

| Тип | Когда использовать | Пример |
| --- | --- | --- |
| `docs` | Новые разделы и правки текста руководства | `docs(accessibility): добавить правила доступности текста` |
| `fix` | Исправление ошибки: неверное правило, битая ссылка, опечатка | `fix(glossary): исправить определение подборки` |
| `ci` | Workflow в `.github/workflows/` и правила линтеров в `styles/`, `.vale.ini`, `.markdownlint-cli2.jsonc` | `ci(vale): добавить проверку текста ссылок` |
| `build` | `mkdocs.yml`, `requirements.txt`, тема сайта | `build: обновить mkdocs-material` |
| `chore` | Всё остальное: `.gitignore`, шаблоны GitHub | `chore: добавить шаблон Pull Request` |

Пример коммита, который меняет правило:

```text
docs(spelling)!: писать «ё» во всех словах

Раньше «ё» писали только там, где без неё возможна ошибка в прочтении.
Теперь «ё» обязательна везде, правило Itmotify.Yo стало ошибкой.
```

## Процесс ревью

1. **Автоматические проверки.** На каждый Pull Request GitHub Actions запускает markdownlint, Vale и сборку `mkdocs build --strict`. Ревью начинаем, только когда все проверки прошли.
2. **Ревьюер.** Нужно одно одобрение от другого участника — не от автора изменения. Ревьюер отвечает в течение 2 рабочих дней.
3. **Комментарии.** Ревьюер начинает комментарий с метки, чтобы автор понимал, что от него ждут:

    | Метка | Значение |
    | --- | --- |
    | `Замечание:` | Нарушено правило руководства, нужно исправить до слияния |
    | `Предложение:` | Можно сделать лучше, автор решает сам |
    | `Вопрос:` | Ревьюеру непонятно, нужен ответ или пояснение в тексте |

4. **Правки.** Автор исправляет замечания новым коммитом в той же ветке и отвечает на каждый комментарий. Историю ветки во время ревью не переписываем, чтобы ревьюер видел, что изменилось.
5. **Слияние.** После одобрения автор нажимает **Merge pull request** и выбирает **Create a merge commit**. Ветку после слияния удаляем.
6. **Публикация.** После слияния GitHub Actions собирает сайт и публикует его на GitHub Pages. Автор открывает сайт и проверяет, что изменения появились.

Что проверяет ревьюер:

- [ ] изменение решает задачу, описанную в PR;
- [ ] правило сформулировано однозначно и с примером «неправильно — правильно»;
- [ ] новое правило не противоречит другим разделам;
- [ ] новый раздел есть в навигации и в таблице разделов на главной;
- [ ] текст изменения сам соответствует руководству.

## Локальная сборка

Нужны Python 3.10 или выше и Git. Для линтеров — Node.js 20 или выше и [Vale](https://vale.sh/docs/install).

1. Установите зависимости в виртуальное окружение:

    ```bash
    python -m venv .venv
    source .venv/bin/activate
    pip install -r requirements.txt
    ```

    В Windows вместо второй команды выполните `.venv\Scripts\activate`.

2. Запустите сайт с автообновлением:

    ```bash
    mkdocs serve
    ```

    Сайт откроется по адресу <http://127.0.0.1:8000> и будет обновляться при каждом сохранении файла.

3. Перед коммитом запустите те же проверки, что и в CI:

    ```bash
    npx markdownlint-cli2
    vale docs README.md CONTRIBUTING.md
    mkdocs build --strict
    ```

    Все три команды должны завершиться без ошибок. Замечания Vale уровня `warning` и `suggestion` сборку не останавливают, но их стоит исправить.

## Как добавить новый раздел

1. Создайте файл в папке `docs/`. Имя — латиницей, строчными буквами, через дефис: `docs/accessibility.md`.
2. В первой строке напишите заголовок первого уровня — название раздела.
3. Добавьте раздел в навигацию `nav` в `mkdocs.yml`, в подходящую группу:

    ```yaml
    nav:
      - Точечные рекомендации:
          - Интерфейс и действия: ui.md
          - Требования и ТЗ: requirements.md
          - Доступность текста: accessibility.md
    ```

4. Добавьте строку о разделе в таблицу «Разделы» на главной странице `docs/index.md`.
5. Если раздел вводит новые термины, добавьте их в `docs/glossary.md`.
6. Если правило можно проверить автоматически, добавьте правило Vale в `styles/Itmotify/` и сошлитесь в нём на новый раздел.
7. Запустите локальные проверки и откройте Pull Request.
